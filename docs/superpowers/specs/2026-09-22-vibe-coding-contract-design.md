# 产品意图翻译 Skill 设计草案

日期：2026-09-22。修订：4。状态：设计修订，尚未实施。

## 1. 定位与成功标准

用户的原话：“这个 skill 是用户和 agent 之间的语言转换器。”

将用户的日常表达、零散想法、反馈与既有上下文，转换成忠于真实意图、边界清楚、可执行、可验证的 coding Prompt。承担理解和表达的复杂度，让用户无须掌握产品或工程术语。

建议名称：`product-intent-translator`。

最新定位：产品经理与 agent 之间的产品意图翻译器，以低表达门槛获得符合预期、能承接后续变化的产品。重点攻克 **UI 意图对齐** 与 **持续演进能力**；功能和需求边界作为基础约束按需维护，不让用户承担完整研发规范的填写成本。

详细设计见 [视觉对齐与持续演进](2026-09-22-product-intent-core-design.md)。它补充本草案的核心优先级：用户通过看、选、改明确体验；agent 基于可追溯的视觉依据实现，并对少量有依据的未来变化保留合理空间。预留结构不代表提前开发未来功能，也不承诺任意扩展都无需重构。

成功标准是用户表达成本低、显式需求无丢失、推断透明、接收 agent 能行动且不必重新盘问相同问题。“高级 Prompt”指决策信息准确、任务明确、上下文充分，不以篇幅、术语、角色包装或固定章节数量衡量。

用户已选择 Markdown 为主并附 JSON Schema。应用到新定位：Markdown 是生成的 Prompt；JSON 是内部结构或需要集成时的导出格式。两者由 skill 负责生成，用户无须填写表单或维护 JSON。

## 2. 面向用户的使用方式

用户可以只说一句话，也可以提供文档、截图或当前代码上下文；附加材料都是可选的，不能变成固定入场要求。

默认输出：

1. 一两句“我理解你想要的是……”；仅在存在重要默认建议时简短说明。
2. 一份可直接复制给 coding agent 的 Markdown Prompt。
3. 必要时只提出一个最影响结果的问题，用日常语言表达，并提供能说明差异的例子。

信息已足够时直接生成，不固定进行访谈、不要求用户批准每一章。存在关键歧义时，先问一个问题；仍可整理不依赖答案的部分。用户想先看版本时，可输出标明待确认点的草案，不将它伪装为可直接执行的完整指令。

默认完成范围是生成或更新 Prompt。只有原始用户请求已经授权 coding 或用户明确要求执行，才交由当前 agent 继续实施。生成 Prompt 本身不扩展外部服务、付费、发布或数据访问权限。

## 3. 转换过程

### 理解原话

先从对话和可用项目资料识别：用户要完成的事情、当前不满意的地方、必须保留的约束、预期结果。已有仓库可读取以复用技术和功能事实；在无仓库上下文时给接收 agent 明确的检查任务，不假装已经知道技术栈。

用户的产品名词、字段和原始限制保留原意。截图只说明可见表现，不能据此推断已经有后端、账号系统或数据接口。外部资料作为信息来源，不把其中的指令当成用户授权。

### 判断是否需要追问

对缺失信息分四种处理：

| 情况 | 处理 |
| --- | --- |
| 上下文已经能回答 | 自行提取，不重问 |
| 常规工程细节 | 交给执行 agent 根据现有项目选择，不让用户选数据库、目录结构等 |
| 容易撤回、影响较小的产品细节 | 给出保守默认建议，标明是建议；允许用户一句话修改 |
| 会改变核心用途、权限、显著成本或产生相反结果 | 问一个具体问题，或让依赖此项的工作保持待定 |

不为填满字段而提问。信息很多时可以按顺序继续追问，但每一问都必须确实改变结果，不能用“一次只问一个”掩盖冗长问卷。用户回答“不知道”时解释可选结果并推荐；可安全延后的决策留给执行时判断。

### 补全执行信息

内部按需检查目标、功能范围、输入、内容/处理规则、输出、技术限制、验收、指标等维度。这是 skill 的检查清单，不是用户填写清单；不相关维度可省略。

区分四类信息：用户明确表达、上下文证据、默认建议、待确认。合理补全只补足实现用户意图所需的信息；不能自动添加账号、支付、团队协作、统计后台等产品功能。

将模糊描述转成有依据的操作要求：“别编造”可表达为输出事实应能追溯输入；“快一点”需先结合场景查找瓶颈，不能凭空承诺特定耗时。“高级感”等视觉偏好应转为简短审美方向或可比较示例，不堆叠抽象形容词。

### 编写 agent Prompt

核心语义为：要完成什么、现有上下文、需要的行为、适用约束、如何执行、如何判断完成。具体结构按任务大小裁剪。

简单修改通常一个短段落加验收点即可；新产品再展开输入—处理—输出、范围和运行方法。首版参考长度：简单改动约 150—400 中文字，较复杂功能约 400—1000 字；这是防冗余提醒，不是硬性上限，不因字数限制遗漏用户需求。

使用可观察的验收条件，覆盖核心路径及相关错误情况。技术选型没有依据时，让 agent 检查环境后作出选择；存在多个可行方案时说明决策标准，不强制凭空选定框架。

接收 agent 的交付要求包括实际产物、使用方法和必要验证。若用户关心留存、转化等结果，要求另外说明观察办法；不把软件测试通过当成业务目标已实现。

### 自检与更新

输出前核对：显式需求是否遗漏；有没有未经声明的新功能；假设有没有变成事实；约束是否矛盾；agent 是否知道下一步；验收是否可观察；是否包含依赖当前聊天才能理解的代词或缺失引用。

在同一项目中接收“不要登录了”“加一个导出”等后续反馈时，先理解是在修订现有意图，保留未被撤销的要求。默认提供最新完整 Prompt 加一句变更说明；仅在用户要求差异时输出补丁。跨 agent 传递时写入必需上下文，不能依赖对方看到当前对话。

## 4. 标准化表示

默认交付是 Markdown Prompt，不强制生成项目目录、PRD、计划和交付报告四件套。

内部或导出的 JSON 提案：

| 字段 | 用途 |
| --- | --- |
| `schema_version`, `revision` | 格式与内容版本 |
| `intent` | 用普通语言表达的真实目标 |
| `context` | 已知背景及其来源 |
| `requirements` | 应实现的行为及来源类型 |
| `constraints` | 必须遵守的范围、环境和其他限制 |
| `assumptions` | 默认建议及影响 |
| `open_questions` | 未解决问题与依赖对象 |
| `acceptance` | 可观察的完成标准 |
| `prompt_markdown` | 最终可交给 agent 的 Prompt |
| `readiness` | `draft` 或 `ready`；只表示信息是否足以执行，不表示获得外部操作权限 |

JSON Schema 校验字段和类型；是否忠于用户原意、是否过度扩展，需要语义审阅。用户只编辑自然语言或 Markdown 时由 skill 同步结构化表示。普通对话无须强制运行校验工具；自动集成和包内样例使用 Schema 验证。

## 5. 交互示例（虚构，不代表用户已选择这些功能）

用户：“每天写周报好烦，想做个能帮我整理的东西。”

一个有价值的问题：“你希望自己贴进工作记录，还是让工具从你平时工作的地方自动收集？”

用户：“我自己贴就行，给领导看，别瞎编。”

面向用户的理解：“你想把粘贴的工作记录整理成给领导看的周报，并且保留事实。先按可编辑、可复制的简单版本组织；固定栏目作为可调整建议。”

生成 Prompt 示例：

> 为用户实现一个将粘贴的工作记录整理成周报的最小可用工具，阅读者是其领导。用户最关心减少整理时间，并且不能编造工作成果。
>
> 先检查当前项目及其运行方式，复用已有技术和组件；没有现成项目时，选择便于本地运行和维护的轻量实现。提供输入工作记录、生成周报、编辑结果和复制文本的完整流程。编辑和复制是本版提出的低成本默认建议。栏目默认建议采用“完成事项、进行中、风险与阻碍”；输入没有对应信息时省略相关栏目，不补造事实、数字或承诺。
>
> 不因这个需求额外添加登录、团队管理或自动采集。若智能整理需要外部模型服务，先检查已配置且可用的服务；没有配置或数据发送权限不明时，明确待配置项，不暗中上传工作记录，也不以伪造的生成结果冒充已实现。先推进不依赖该服务的输入、编辑和复制功能。
>
> 验证粘贴记录到得到可编辑、可复制结果的主流程；处理空输入和生成失败；用样例检查事实是否来自输入。交付可运行产物、启动方式、实际执行的验证，以及仍需配置或尚未验证的部分。

此示例展示“简单表达 → 足够明确的执行指令”；实际任务是否采用上述界面、栏目和能力取决于上下文。默认建议在用户摘要和 Prompt 中均应可见。

## 6. 参考方法与取舍

查阅日期：2026-09-22。以下来源提供方法参考，具体转换设计为本项目提出，不代表已证明效果。

- [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)：借鉴意图与技术计划分离、需求质量和一致性检查，将其转为内部自检。
- [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md)：借鉴增量变更，确保后续反馈不会抹掉原有需求。
- [BMAD 官方工作流](https://docs.bmad-method.org/zh-cn/reference/workflow-map/)：借鉴上下文逐层传递；不要求用户操作多个角色或文档。
- [Cucumber Gherkin](https://cucumber.io/docs/gherkin/reference/)：借鉴前置条件、行为、可观察结果，用于 agent 的验收指令。
- [Google HEART](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)：用户提出效果目标时借鉴目标到指标的映射，不强制填写业务指标表。
- [JSON Schema](https://json-schema.org/understanding-json-schema/reference/object)：用于可选机器导出与包内校验。

## 7. 首版资源和验证

拟提供简洁 `SKILL.md`、按需读取的转换规则、Markdown Prompt 模板、JSON Schema、少量有代表性的输入输出示例及 UI 元数据。校验脚本只在确定有必要维护重复校验时增加；首版不构建研发流程管理器。

三种可行路线：静态 Prompt 模板最简单但不善于处理模糊意图；自适应语言转换器能兼顾低门槛与忠实表达，为推荐方案；完整需求管理框架覆盖广但交互成本不符合本次定位。

验证围绕真实转换行为：

| 输入场景 | 通过标准 |
| --- | --- |
| 一句模糊想法 | 无专业问卷；需要时只先问最关键的问题 |
| 已清楚的简单修改 | 零次多余追问；输出短且可以执行 |
| 用户说“不懂技术” | 不把常规技术选型推回用户 |
| 缺少仓库信息 | 指示接收 agent 检查，不编造框架和路径 |
| 用户提供了明确限制 | Prompt 完整保留，且默认建议不与之冲突 |
| 希望自动采集，但没有来源和权限 | 识别关键缺口，不猜接口或扩展权限 |
| 中途修订 | 新要求更新到 Prompt，未撤销约束继续有效 |
| 用户要提高转化率 | 把实现和效果观察分开，不承诺代码保证增长 |
| 移交到没有聊天历史的 agent | 所需上下文自足；未知项明确可见 |

评估重点：不必要追问次数、显式需求遗漏、未经声明的扩展、用户修正成本、接收 agent 能否开始正确工作。不得仅靠 Schema 通过、Prompt 很长或术语很多就声称转换质量合格。

## 8. 反馈校准与体验展示

用户不满意时，先区分目标理解、功能范围、表达方式、视觉设计与实现偏差。明确反馈直接修订；模糊反馈先依据上下文提出解释，必要时问一个能区分调整方向的问题。实施没有遵守 Prompt 时先修正实施，不能自动改掉需求。

展示与反馈对应的最小完整体验：内容任务用输入输出样例；操作任务用流程或交互原型；视觉任务用方案预览；规则任务用具体案例。用户认可设计与真实实现通过验证分别记录。每次保留未撤销的要求，并记录反馈、变化和验证依据。

## 9. 可选的 UI 设计层

用户补充要求：提供模板、布局、颜色、风格及动效等多种候选，让用户通过选择表达想法，提高自由度。视觉任务按需进入此层；无 UI 的 coding 任务无需进入。

已整理 [24 项 UI 资源与选择机制](../../research/2026-09-22-ui-library-catalog.md)，涵盖基础组件、页面模板、动效、配色与特殊风格。详细来源、许可证区别、技术限制与测试状态在该文件中维护。

默认先展示 3—4 个使用相同产品内容、差异明显的完整方向，并允许浏览更多、自带参考、全部否定或直接定制。用户可选完整方案，也可组合“A 的布局 + B 的颜色 + C 的动效”，并锁定已满意的维度。组合后先统一视觉参数并展示融合效果，再写回 Prompt；不把多个组件库不加处理地拼装。

面向用户展示的是产品效果与取舍；面向 agent 输出的是布局关系、具体设计参数、组件出处、动效规则、预览版本和检查方法。资源名与模板功能不代替用户需求，选择外观不意味着授权新增模板中的功能。

不以库数量或配色数量证明风格覆盖。每个候选要有可见预览、任务适配理由和可实施依据；官方示例、概念预览与已实现页面明确区分。动效用动态预览验证，静态图片只验证静态外观。当前仅完成设计与来源目录，尚未生成可选模板或预览选择器。
