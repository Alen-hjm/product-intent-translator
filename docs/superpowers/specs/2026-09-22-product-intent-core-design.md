# 产品意图翻译器：视觉对齐与持续演进

日期：2026-09-22。状态：设计草案，行为尚未实测。

## 定位

目标：以尽可能低的表达与决策成本，让产品经理得到接近心中预期、能够继续演进的产品。产品经理指负责产品目标和取舍的人，不要求具备专业术语或研发知识。

核心攻克两个问题：

1. 用户的 UI 想法难以准确表达，agent 难以稳定理解与还原。
2. Vibe Coding 的想法持续出现，初版针对几个功能设计，后续增加能力时容易推翻结构、破坏一致性或损伤旧功能。

需求和功能边界作为必要基础保留，以最少交互维护。涉及数据、权限和跨角色流程时，边界仍可能复杂；不能为了突出 UI 而省略这些约束。

“优秀产品”是目标，不是 skill 能保证的结果。首版把品质落实为：核心任务可完成、视觉与体验符合已认可方向、基础可用性得到验证、常见变化能够以合理成本承接。市场价值和长期业务效果需要另行验证。

## 主线一：将视觉意图转为可靠实现

### 表达入口

支持自然语言、参考页面、截图、方案比较、局部选择与 DIY 操作。用户可任选入口，不必按阶段填写问题。参考中只采纳用户喜欢的属性，不自动采用参考产品的功能或全部样式。

先判断反馈作用于信息层级、布局、风格、密度、内容素材、交互还是实现偏差。明确反馈直接处理；含糊反馈优先通过差异可见的小样或局部对比定位，避免连续口头盘问。

### 共享的视觉依据

保存用户实际看过的预览及版本、选中项、排除项、锁定维度、修改范围和变更原因。将其转换为布局关系、语义色、字体层级、间距、组件变体、动效和响应式行为。

具体参数来自选中预览、用户操作或明确标注的建议。不能把没有出现过的参数写成用户已确认。用户只认同整体风格时，细节仍为可修订建议。

### 连续反馈

推荐方向 → 局部或整体预览 → 用户选择/编辑 → 融合预览 → agent 实现 → 实际页面对照。用户随时可以修正，未撤销的目标和偏好持续有效。用户选择外观不等于接受模板内附带的新功能。

版本差异应具体到修改对象：哪段文案、哪个区块、哪个主题变量、哪些屏幕尺寸。依赖工具获得的结构化操作优先于截图猜测；没有编辑工具时，采用选中区域的自然语言反馈和前后对比，并说明能力限制。

### 成功依据

用户认为方向接近预期；实际页面保留选择结果；已认可部分不会在无关修改中反复变化；真实内容、长文本、空状态、移动尺寸和交互状态仍然可用。静态图不证明动态交互正确，视觉相似也不证明核心任务完成。

## 主线二：为合理变化保留空间

### 先识别变化，避免预测所有功能

依据用户已提到的后续想法、产品的实际结构和仓库现状，选取少量有依据的变化场景。常规项目可先考虑一两个，例如增加一种记录字段、增加一个视图或替换一种数据来源；不相关的场景不机械套用。

每个场景记录其来源：用户明确计划、现有代码证据或 AI 推测。AI 推测不能变成本轮功能要求。没有可信演进线索时，只做低成本的结构整理，并明确不承诺未来任意变化都无需重构。

用户只需决定真正影响产品路线的事项。可以问“以后可能给同事一起用吗”，不让用户回答“是否采用多租户架构”。即使用户说可能多人使用，也不因此立即实现账号、角色和权限系统。

### 按实际变化设计

| 变化方向 | 当前值得考虑的结构 | 不应自动产生的工作 |
| --- | --- | --- |
| 换主题或局部风格 | 语义样式变量、清晰组件变体、必要的共享规则 | 给每一项 CSS 都开发可视化编辑能力 |
| 新增页面或视图 | 稳定的页面结构、清楚的数据入口，适度复用共同部分 | 为单页工具搭建通用低代码平台 |
| 新增字段、分类或状态 | 数据表示与界面展示避免无必要绑定；已有持久数据有迁移办法 | 为所有字段建立可配置模型引擎 |
| 接入另一种数据来源 | 在确有变化可能时隔离读写和外部调用，保持业务含义明确 | 预建大量空接口或全套插件系统 |
| 从单人走向协作 | 若有明确路线，评估数据归属和未来迁移代价 | 未授权就添加账号、计费和复杂权限 |
| 长列表或更多数据 | 在预计数据量下选择合理展示和读取方式 | 为小工具预建分布式基础设施 |

以上都是条件性判断，不能当作所有项目的强制架构。现有项目优先沿用已形成的结构，只有与本次变化相关的问题才做针对性改进。

### 将扩展成本翻译给产品经理

只呈现影响决策的取舍，例如：“把分类单独保存会多一点实现工作，但以后增加分类不需要重做记账页面。”对于明显增加首版成本的预留，说明收益依据和替代方案，再由用户决定。

不可逆或代价高的决定应显式记录；日常实现细节由 agent 处理。未来需求变得具体时重新评估，允许合理重构，不追求永远不改基础结构。

### 用变化验证结构

不能只写“架构可扩展”。设计阶段做影响推演：这个变化会改到什么、会不会破坏数据和旧流程、需要什么迁移。推演必须标明未执行。

实施阶段在有价值且获得执行授权时，对一个代表性变化做有限验证，可在临时分支、隔离目录或已有测试机制中进行。只验证结构能力，不把试验功能擅自合入正式产品。没有代码时不能声称完成扩展验证。

评估局部性、旧行为保持、数据兼容与成本是否匹配场景。修改文件数量仅作诊断线索，不设“越少越好”的机械标准。

## 两条主线的连接

设计系统兼顾用户审美与后续变化：一致的语义样式、可复用但不过度通用的组件、明确的数据与展示关系，使后续新增功能继续沿用已认可的视觉语言。

新想法到来时，先识别影响目标、数据、流程、布局、组件还是技术依赖；读取当前已认可的产品理解和实现状态，再决定局部修改、结构调整或需要用户取舍。变更不自动覆盖锁定的视觉偏好，也不为了保留原型外观而掩盖必要的功能设计变化。

UI 和扩展性发生冲突时展示具体原因。例如导航无法容纳新增模块，应给出新的组织方式及对已有操作的影响，不能仅把字号缩小或不断塞入按钮。

## 输出仍保持低门槛

面向用户：可见体验、简短解释、必要取舍以及本轮实际完成情况。

面向 agent：产品目的和约束、选定的视觉依据、当前实现事实、修改要求、有依据的演进场景、当前应保留的结构、验证方法和未确认信息。内部结构化表示由 skill 维护。

不为所有任务强制生成架构报告。简单任务只输出必要的局部指令；复杂任务才附设计与演进说明。可编辑原型、运行预览和代码操作依赖实际工具，skill 负责协调和解释，不虚构工具能力。

## 首版验证

用同一小产品的连续迭代验证，而不是只测试一次生成：

1. 从少量功能的自然语言输入生成设计与实施要求。
2. 用户否定某种 UI，检查反馈是否准确收敛而没有丢失业务目标。
3. 用户组合外观和布局，检查融合后的预览与 agent 输出是否一致。
4. 在初版完成后加入一个此前未具体设计、但合理相关的新需求，检查变化如何被承接。
5. 核对已有数据、原功能、锁定的视觉选择和主要操作路径。
6. 对比普通对话流程，记录重复解释、误改、实施偏差、返工及结构调整成本，并同时记录首版的额外成本。

真正的优势应由“双重结果”证明：审美意图更容易对齐，后续改动更容易落地。不能以库数量、Prompt 长度、抽象层数量或文档完备程度替代这些结果。
